# 项目现状与优化计划

本轮梳理基于 `a90b85c`（2026-10-23），以实际入口、调用链和离线复现为依据。已有架构文档中的功能描述不能直接作为实现完成度或性能证据。

## 实际运行结构

React 页面通过相对 `/api` 请求访问 FastAPI。开发环境由 Vite 代理到 8010，容器环境由 Nginx 代理到后端；React 入口是 `frontend/src/App.tsx`，API 入口是 `scripts/run_api.py` 和 `src/chatterpal/web/api_server.py`。

Gradio 通过 `python -m chatterpal.web.app` 独立启动。两个 Web 入口共用配置和提供商工厂，进程内的会话、缓存及用户历史各自保存，没有数据库或跨进程状态同步。

| 层次 | 实际职责 | 主要代码 |
| --- | --- | --- |
| Web 接口 | 请求和响应模型、音频上传/下载、场景与音色查询 | `web/api_server.py`、`web/app.py` |
| 对话 | 会话、历史、ASR → LLM → TTS、主题上下文 | `services/chat.py`、`services/topic_generator.py` |
| 提供商 | 本地 Whisper / Aliyun NLS、Edge / CosyVoice、百炼 / OpenAI | `core/asr/`、`core/tts/`、`core/llm/` |
| 评估 | 基础评分、文本对照、声学和韵律特征、AI 文字建议 | `core/assessment/`、`services/correction.py`、`services/evaluation.py`、`services/ai_correction.py` |
| 资源与配置 | Settings、工厂、音频处理、缓存、偏好 JSON | `config/`、`utils/` |

API 当前公开十条路由：根路径、健康检查、文本聊天、音频聊天、基础发音分析、AI 发音分析、场景列表、场景详情、音色列表及音频下载。前端主要提供对话和发音纠正两个页面。

## 已确认的能力边界

- ASR、LLM 和 TTS 有实际提供商实现。ASR 的质量分与置信度包含应用自己的启发式规则，不能直接当作识别引擎的原始置信度。
- `PronunciationCorrector.assess()` 当前仍创建固定的演示评分：总分 75，其他维度也是固定值。详细分析没有形成经过校准的声学评分模型。
- `PhonemeAnalyzer` 能提取整段音频的声学统计特征，目前没有按参考文本进行音素切分、强制对齐或准确率验证。
- `ProsodyAnalyzer` 部分指标来自 myprosody，部分为默认或估计值；缺少依赖的情况需要与成功分析明确区分。
- AI 纠错路径存在报告字段和提示词格式化问题；文档中的“AI 分析”不能据此视为已经稳定运行。
- Gradio 当前实际聊天页面与 `web/components/` 中的丰富组件并非同一套接线。评分和纠错页仍有演示回调；实际聊天回调固定传入 `default_web_session`，没有保存新建会话返回的 ID。服务入口离线复现中，连续发送两次消息创建了两个会话，第二次历史仅包含第二轮，浏览器会话状态需要单独修复。
- 全量测试收集被 17 个原有测试文件的语法错误阻塞，不能以 README 中的覆盖率或成熟度声明代替验收。

## 第一批：聊天请求链路

### 优化前证据

`/api/chat/audio` 先同步识别音频用于返回转写，再调用 `ChatService.chat_with_audio()` 对同一文件重新识别。Gradio 的 `process_chat()` 也会为了显示文本而重复识别。不同次转写可能不一致，使页面文本和实际 LLM 上下文不同。

`/api/chat` 直接在异步路由里执行同步 LLM 调用；音频路由的第一次 ASR 调用也在事件循环中执行。慢识别或慢网络请求会阻塞健康检查及其他请求。

离线基线使用真实 API 路由、ChatService、ASR 基类质量检查和 EdgeTTS，仅替换外部识别、模型及合成边界。每次 ASR 和 LLM 固定等待 150 ms，运行结果为：

| 路径 | 请求耗时 | 最大事件循环停顿 | 成功音频请求的 ASR 次数 |
| --- | --- | --- | --- |
| 音频聊天 | 464.8 ms | 161.6 ms | 2，其中 1 次在 API 线程 |
| 文本聊天 | 154.3 ms | 156.4 ms | 不适用 |

这些数字仅用于比较同一离线负载下的调用结构，不代表真实模型、云端服务或生产部署的延迟。

### 实施目标

1. 在服务层保留一次识别的转写和回复结果，供 API 及 Gradio 复用；保留原 `chat_with_audio()` 的三元组返回接口。
2. 将同步 ASR、LLM 和 TTS 调用从 API 事件循环移至工作线程。
3. 同一会话的文本对话轮次按顺序更新历史，不同会话可并发调用模型。
4. 模型失败时不留下未配对的用户消息；保留音频上传独立命名和异常清理。
5. 使用可控事件和调用计数测试上述行为，再以真实 HTTP socket 验证健康检查、聊天、下载与清理。

### 实施与验证结果

本批增加不可变的 `AudioChatResult` 和 `chat_with_audio_result()`，把同一次识别的转写、回复、音频及会话 ID 一并返回。API 与 `process_chat()` 使用该结果；原 `chat_with_audio()` 仍返回三元组，HTTP 响应字段保持一致。同步 ASR/LLM/TTS 在工作线程执行；文本对话的上下文生成和成对写入由会话锁保护，LLM 失败不会留下未配对的用户消息。

同一离线脚本和同一固定负载的优化后结果：

| 路径 | 请求耗时：优化前 → 优化后 | 最大事件循环停顿：优化前 → 优化后 | 识别次数 |
| --- | --- | --- | --- |
| 音频聊天 | 464.8 → 310.3 ms | 161.6 → 6.0 ms | 2 → 1，API 线程内调用从 1 → 0 |
| 文本聊天 | 154.3 → 154.8 ms | 156.4 → 5.7 ms | 不适用 |

音频请求减少约三分之一耗时来自省去一次模拟的 ASR 调用；文本请求的单次总等待时间基本不变，改进体现在慢调用期间其他请求仍可运行。上述为单轮离线机制验证，不是生产延迟承诺。

联合离线回归为 **88 项通过**，包含原有 80 项和新增单次识别、健康检查响应性、旧接口兼容、Gradio 复用、同会话有序、不同会话并发及 LLM 失败恢复测试。真实 Uvicorn HTTP socket 验证通过文本聊天、multipart WAV 聊天、音频下载、慢提供商期间的健康检查、历史一致性和上传清理；外部识别、模型和合成仍使用受控离线边界。服务器及测试音频均在验证后清理。

独立复核未发现本批改动引入的可确认回归：另行运行的 44 项相关回归全部通过；使用真实 ASR 基类的离线探针验证了识别重试、空识别、旧接口和 TTS 失败仍返回文本，ASGI 探针验证了同会话失败恢复和不同会话并发。这 44 项属于相关回归的复跑，不计为新增测试数量。

本批保留现有语音请求进入 ASR 的顺序、TTS 音色选择和返回文件格式。验证范围限于聊天调用链；其他接口的阻塞调用、Gradio 浏览器和默认麦克风元组输入、线程池饱和、请求取消，以及会话创建、删除和过期清理的并发行为尚待后续验证。

## 后续批次与验收标准

| 顺序 | 方向 | 当前代码证据 | 最小验收标准 |
| --- | --- | --- | --- |
| 2 | 修复分析接口契约和临时文件所有权 | `CorrectionReport` 没有 API/AI 调用方读取的 `recognized_text`；两个分析器按临时目录前缀清理，可能删除调用方的输入文件；前端基础分析使用 `score/original_text`，服务端返回 `overall_score/recognized_text` | 基础分析端到端返回并显示真实转写；调用方文件在成功/失败时均保留；内部文件均清理 |
| 3 | 恢复可信的测试门槛 | 17 个旧测试语法错误；部分测试仍模拟旧接口；默认覆盖率门槛没有完整测试结果支撑 | 全量可收集；历史失败逐项确认与修复；只设定实测可解释的覆盖率要求，接入自动检查 |
| 4 | 录音、播放和请求生命周期 | `blob:` URL 被当作 Base64 拼接；录音缺少卸载清理；对象 URL 未释放；清空聊天后旧请求仍可能写回；MediaRecorder 数据只改 MIME 标签并未转码 | 录音离开页面会释放麦克风；自己的录音可回放；URL 及时释放；过期响应不恢复旧会话；上传字节和格式一致 |
| 5 | Whisper 模型和音频处理复用 | 当前 SpeechRecognition 的 Whisper 入口每次调用 `whisper.load_model()`；文件识别先读取半秒用于环境噪音调整；默认语言为中文；ASR 基类把连续十个以上英文字母作为疑似错误扣减置信度 | 实例内受控复用模型并限制并发显存/内存；明确英语练习的语言和置信度策略；保证录音开头不丢失；测量冷启动、热请求和峰值内存 |
| 6 | 评估可信度和提供商接线 | 固定分数、缺失维度被当零分、部分真实特征未进入报告、AI 提示词大括号格式化错误 | 标识每项结果来源与可用状态；没有证据的维度显示不可评估；使用有标注样本验证评分，而非仅检查分数非负 |
| 7 | 打包和部署体积 | 公开 CLI 指向未进入 wheel 的 `scripts` 包；所有部署必装本地推理与设备录音依赖 | 干净目录安装后公开命令可运行；云端模式不需本地推理依赖；明确 CPU 安装方案并实测镜像大小 |

同时应处理 Gradio 的浏览器会话状态、音频输出真实格式、生成音频及过期会话的生命周期。这些更改应分别建立回归，不宜在移走阻塞调用时顺手混入。

可维护性方面，`services/chat.py` 与 `core/tts/base.py` 均已超过千行，混合了提供商调用、缓存、播放、界面适配和会话操作；TTS 基类还存在同名方法后定义覆盖前定义的情况。应在上述行为测试稳定后，再逐步拆分职责和清理重复实现。

## 本轮验证边界

本轮优先在离线边界验证调用次数、线程位置、状态一致性及异常清理。不用真实云端密钥，不下载 Whisper 模型，也不把固定时延模拟当作模型推理速度提升。后续模型复用和评分改进需要各自的数据集与测量方案。

在仓库根目录可复跑本批验收：

```bash
uv run python -m pytest -o addopts='' -q \
  tests/test_chat_pipeline.py \
  tests/test_aliyun_asr_concurrency.py \
  tests/test_config.py \
  tests/test_configuration_contract.py \
  tests/test_edge_tts_async.py \
  tests/test_api_tts.py \
  tests/test_docker_deployment.py \
  -W error::RuntimeWarning
```

这里显式覆盖全仓覆盖率选项，仅作为本批回归门槛。全量收集和原有失败修复后，再恢复统一的覆盖率验收。
